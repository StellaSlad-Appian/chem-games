## 1. Real, pre-existing on master

### `i18n.spec.ts:1307` — Russian rendering › the cheat-sheet index, including its category and year-level labels

```
Error: expect(locator).toBeVisible() failed
Locator: getByText('14 тем')
Expected: visible
Timeout: 10000ms
Error: element(s) not found
```

**Cause.** The index now renders **15** sheets; the assertion still says 14.

The 15th is `relative-formula-mass`, added on master in `4cebddf`. That commit
did not update this assertion. Verified:

- `4cebddf:src/lib/cheat-sheet-data.ts` has 15 `slug:` entries;
- `4cebddf:e2e/i18n.spec.ts:1323` asserts `'14'`;
- `git diff 4cebddf HEAD -- e2e/i18n.spec.ts` is **empty** — none of the merged
  work touches this file.

So master `4cebddf` fails this test on its own.

**The fix is not "bump the digit".** The comment directly above the assertion
says so, and it is right:

> Fourteen sheets selects the `many` category in Russian … **Fifteen would not.**
> At 15 Russian is still `many`, but at 21 it is `one` and at 22 it is `few` — so
> whoever adds the twenty-first sheet has to move this assertion rather than bump
> the digit.

15 is still `many`, so changing `'14'` to `'15'` restores the test *and* keeps it
exercising the plural form it exists for. That is the correct fix today. The
deeper problem is that the assertion is coupled to a count that any new sheet
changes, which is why it has now broken twice in two days (13→14 on the split,
14→15 here).

**Worth considering instead:** assert against `CHEAT_SHEETS.length` computed in
the spec rather than a literal, with a separate assertion pinned to a fixed
number that exercises `many`. Then adding a sheet cannot break it.

## 2. Locale negotiation — fails under `next start` on master too

Three failures, all `expect(page).toHaveURL(expected) failed`:

| Spec | Test |
|---|---|
| `i18n.spec.ts` | French negotiation › the switcher moves the reader to French and remembers it |
| `i18n.spec.ts` | Spanish negotiation › an unprefixed URL redirects and the switcher remembers Spanish |
| `nav.spec.ts` | phone navigation › reaching everything else on a phone links to … |

**Evidence these are not ours.** Earlier the same night, on plain master with no
merged work, `next start` produced:

- `i18n.spec.ts` alone → 3 failed (Spanish, Italian, Russian switcher)
- `explore-archive.spec.ts` + `i18n.spec.ts` → 1 failed (a ru reflow test)

and the *set* changed between runs. The same family is green under `next dev`:
the widget agent measured 330 passed / 1 failed there.

**This is its own defect, unrelated to this work:** locale-cookie negotiation
behaves differently under `next start` than under `next dev`, so the suite cannot
currently be trusted in one mode without knowing which. Worth a ticket.
